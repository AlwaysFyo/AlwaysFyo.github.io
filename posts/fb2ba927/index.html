3. 数据驱动

3.1 背景/介绍

问题背景

在没有使用数据驱动之前，我们可能会遇到因为一些数据带来的问题，我们来看两个例子。

当测试数据多起来的时候，代码中重复内容就会比较多，例如下面 3 个测试数据需要分别通过代码调用 3 次相同的测试函数，代码就会显得相当臃肿。

再比如，现在同样存在多个测试数据，我的测试函数中会进行断言。下面这段代码没有数据驱动，如果运行到中间用例数据时断言报错了，就会出现后面的用例数据执行不到的情况，导致测试不完全。

定义

  • 数据驱动：在自动化测试中处理测试数据的方式。
  • 参数化：是把测试过程中的数据提取出来，通过参数传递不同的的数据来驱动用例运行，其实也就是数据驱动的概念。

在自动化测试运行时，数据驱动框架会读取数据源中的数据，把数据作为参数传递到功能函数中，并会根据数据的条数多次运行同一个功能函数。

数据驱动的好处

  • 数据驱动能够减少重复代码。
  • 实现测试数据和测试逻辑的解耦，数据所属的测试用例执行失败，不会影响到其他测试数据对应的测试用例。

3.2 使用方法

在 Python 中，应用比较广泛的两个数据驱动的框架：

  • 一个是 DDT (Data-Driven Tests)，它是我们前面 unittest 框架中提到实现数据驱动的不二之选。
  • 另外一个是 parameterized，它是 pytest 能够实现数据驱动的秘诀。

这里我们着重介绍一下 parametrize 是如何使用的。

3.2.1 Parametrize

在 pytest 中，数据驱动是经由 pytest 自带的 pytest.mark.parametrize() 来实现的。

pytest.mark.parametrize 是 pytest 的内置装饰器，它允许你在 function 或者 class 上定义多组参数和 fixture 来实现数据驱动。

@pytest.mark.parametrize(args_name, args_value, ids=new_name) 装饰器必填两个参数：

  • args_name（必填）：参数名。以字符串的形式存在，它代表能被被测试函数所能接受的参数，如果被测试函数有多个参数，则以逗号分隔。
  • args_value（必填）：参数值（列表，元组，字典列表，字典元组）。用于保存测试数据，有多少个值用例就会执行多少次。如果只有一组数据，可以列表的形式存在；如果有多组数据，可以列表嵌套元组的形式存在。
  • ids（可选）：自定义每条用例的名称，如果不指定名称则系统会自动生成每条用例的名称，默认是将所有测试数据拼接起来组成一个名称。

3.3 数据源选择

数据驱动的数据源可以是函数外的数据集合、CSV 文件、Excel 表格、TXT 文件，以及数据库等。

数据源 优点 缺点
Excel 生成数据方便 二进制文件不利于版本管理
CSV 可使用 Excel 编辑 文本格式方便版本管理
YAML 格式完备、可读性好 格式简单
XML 格式完备 冗长复杂
JSON 格式完备，可读性一般 不能编写注释，格式死板

当测试数据量大且结构类似时，推荐采用 Excel 或 CSV 作为外部数据源。

使用 Pytest 支持外部文件实现数据驱动的思路：

  1. JSON/YAML 文件实现数据驱动
    • 创建一个读取 JSON 文件和 YAML 文件的方法
    • 实现自动读取 JSON 文件和 YAML 文件，并把 JSON 文件和 YAML 文件中的数据提取出来，并按照 pytest.mark.parametrize 可接受的方式将数据返回。
  2. Excel 文件实现数据驱动

在 python 中，读写 Excel 的 library 有很多，常见的有 xlrd、xlwt、openpyxl（推荐）、Pandas 等。

核心思路：将读取的 Excel 文件中的数据读取出来， 作为 @pytest.mark.parametrize() 的参数即可。

不管选择哪个数据源，总体的思路都是不变的，都是先通过代码写一个工具来获取到数据源中的数据，然后将这个数据传到 parametrize 中进行测试即可。

4. Mock 接入

4.1 使用背景

在前面的 unittest 框架章节中，已经提到过 mock 是什么，并且讲解了 unittest 中 mock 是怎么用的，接下来看看在 pytest 中是如何使用 mock 的。

在此之前，先来简单回顾下 mock 的概念。mock 测试就是在测试过程中，对于某些不容易构造或者不容易获取的对象，自行创建一个虚拟的对象以便测试的测试方法。这个虚拟的对象就是 mock 对象，mock 对象就是真实对象在调试期间的代替品。

常见 Mock 适用场景：

  • 前后端联调：当前端需要的接口后端还在开发，就可以使用 mock 模拟后端返回我们需要的数据。
  • 单元测试：当我们所要测试的接口还未开发完，而我们还要完成测试用例代码的编写，我们可以先模拟这个接口进行测试。
  • 屏蔽无关的真实服务：专注于要测试服务本身，而其它服务又不在本次测试范围内，则可以使用 mock 只模拟出我们关注的服务。
  • 依赖第三方接口：当我们的接口需要调用第三方，而第三方接口我们还未得到权限或未购买时，可使用 mock 模拟进行测试。

注意 mock 只适合用于临时的测试，而不能代替真实场景的测试。

4.2 搭建方案

Mock Server 的搭建有两种方式，分别是借助第三方工具直接提供 Mock Server，以及自主编码实现 Mock Server。

常见的第三方 Mock Server 工具：Postman、easy-mock、Yapi、Mockjs、mockserver、Moco、lyrebird

5. Logging 日志

在写自动化测试用例时，添加有用的 log 日志信息是非常有必要的。比如在初期的调试过程中，一旦运行有问题，就可以通过日志获取到精确的调试信息。而等到后期稳定运行了，其他测试代人员也可以通过日志信息很容易上手这些用例，所以大家一定要重视测试用例的调试信息。

5.1 介绍

作为初学者的时候，我们常用 print 语句打印日志来调试代码。

但是 Python 中提供了一个日志模块 logging，可以通过它存储各种格式的日志，其主要用于输出运行日志。另外，也可以设置输出日志的等级、日志保存路径、日志文件回滚等。

使用 logging 的优势：

  • 你可以控制消息的级别，过滤掉那些并不重要的消息。
  • 你可决定输出到什么地方，既可以打印到标准输出流中，也可以保存到远程自己的服务器里
  • 你也可以决定怎么输出，更加的定制化，有许多的重要性别级可共选择：debug、info、warning、error 以及 critical。通过赋予 logger 或者 handler 不同的级别，你就可以只输出错误消息到特定的记录文件中，或者在调试时只记录调试信息。
级别 对应的值
CRITICAL 50
ERROR 40
WARNING 30
INFO 20
DEBUG 10
NOTSET 0

5.2 日志格式

格式 作用
%(levelno)s 打印日志级别的数值
%(levelname)s 打印日志级别的名称
%(pathname)s 打印当前执行程序的路径，其实就是 sys.argv[0]
%(filename)s 打印当前执行程序名，python 如：login.py
%(funcName)s 打印日志的当前函数
%(lineno)d 打印日志的当前行号，在第几行打印的日志
%(asctime)s 打印日志的时间
%(thread)d 打印线程 ID
%(threadName)s 打印线程名称
%(process)d 打印进程 ID
%(message)s 打印日志信息

@allure.epic() epic 描述 BDD Style Marker 有 Epic、Feature、Story 三个层级的装饰器，Epic 是 User Story 逻辑上的集合
@allure.feature 模块名称 BDD Style Marker 比 Epic 低一级，可以代表模块
@allure.story 用户故事 BDD Style Marker 比 feature 低一级，代表用户故事（User Story）
@allure.title 用例标题 测试用例的 title
@allure.testcase() 测试用例的链接地址 可以直接给 jira 地址，可以把测试代码和测试用例 link 起来
@allure.issue() 缺陷 对应缺陷管理系统里面的链接
@allure.description() 用例描述 测试用例的描述
@allure.step() 操作步骤 测试用例的步骤
@allure.severity() 用例等级 blocker、critical、normal、minor、trivial
@allure.link() 链接 定义一个链接，在测试报告展现
@allure.attachment() 附件 为测试报告添加附件
